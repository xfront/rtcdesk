# 2026-06-05

## H.264 黑屏修复（第二轮）

用户报告 fMP4/MSE 路径仍然黑屏。日志显示 RTP→depacketizer→muxer 路径正常（SPS 解析 1920x1080，init segment 681 bytes，media segments 正常生成），但 MSE 始终未初始化。

### 根因 1：MSE JS 代码构建语法错误（view.rs）

Rust raw string `r#"..."#` 中的 `\"` 是字面字符 `\` 和 `"`，拼接后 JS 引擎看到：
```javascript
sb.appendBuffer(b64ToBuf(\INITB64\"));  // ← 语法错误！
```
整个 `document::eval()` 静默失败 → MSE 从未初始化 → 黑屏。

**修复**：改用两步法——先 `window._videoInitB64 = '...'` 设变量，再用 `r##"..."##` 执行 MSE setup JS。

### 根因 2：fMP4 trun box flags 与数据不匹配（muxer.rs）

`trun_flags = 0x0100 | 0x0200` 只声明了 sample_duration + sample_size，但实际写入了 5 个字段：
- sample_count + data_offset + first_sample_flags + sample_duration + sample_size

浏览器按 flags 解析时把 data_offset 误读为 sample_duration，sample_flags 误读为 sample_size → MSE 解码失败。

**修复**：`trun_flags = 0x0001 | 0x0004 | 0x0100 | 0x0200`（加上 data_offset_present + first_sample_flags_present）。

## H.264 黑屏修复（第三轮）

用户报告仍然黑屏。日志显示 init segment、media segments 正常生成，SPS 1920x1080 正确。

### 根因 1：tfhd box flags 与数据严重不匹配（muxer.rs）🔴 致命

`tf_flags = 0x02 | 0x08 | 0x10 | 0x20` 声明了 base-data-offset-present(需8字节) + sample-desc-index(4字节) + default-duration(4字节) + default-size(4字节)，期望 24 字节数据。但代码只写了 16 字节（track_id + 3个u32），浏览器解析 moof 时读取越界 → **所有帧被拒绝**。

**修复**：改用 `default-base-is-moof` (0x020000) 简化 tfhd，只写 track_id（4字节），所有 sample 信息由 trun 承载。data_offset = 108（moof 100字节 + mdat header 8字节）。

### 根因 2：encoder 双重 Annex B 起始码（encoder.rs）

OpenH264 `nal_unit()` 返回的数据已包含 `00 00 00 01` 起始码，encoder 又额外加了 START_CODE，导致：
```
first16=[00 00 00 01 00 00 00 01 67 42 C0 28...]  // 双重起始码
first_nal_type=0  // byte[4]=0x00 而非 0x67
```

**修复**：检查 NAL 数据是否已以起始码开头，有则不重复添加。

### 根因 3：MSE JS 竞态条件（view.rs）

`_appendVideoChunk` 检查 `v._sb` 是否存在，但 `_sb` 在异步 `sourceopen` 事件后才设置。chunks 在 eval() 和 sourceopen 之间到达时被静默丢弃。

**修复**：添加 `v._preSbChunks` 缓冲区，`sourceopen` 后自动 flush。同时优化 chunk 传递方式（避免 220KB+ base64 做 eval 拼接，改用全局变量+简单函数调用）。

### 其他修复

- peer.rs：Skip 帧（0字节）跳过写入，不发送空 RTP sample
- 上一轮修复的 encoder.rs（AVCC→Annex B）、feed_nals、avcc_box 仍然有效

## H.264 黑屏修复（第四轮）

用户报告：没收到 IDR 包；还是黑屏；client 断开后还在不停发包。

### 根因 1：Host 不响应 PLI 请求，缺少周期性 keyframe（peer.rs + encoder.rs）🔴 核心问题

客户端每 3 秒发 PLI（Picture Loss Indication），但 webrtc-rs 0.20 alpha 的 `PeerConnectionEventHandler` 无 RTCP 回调。Host 完全忽略 PLI，不会强制编码器产出 IDR 帧。

- 首帧虽然编码为 IDR，但如果客户端因 ICE 延迟错过首帧，后续永远只收到 P 帧
- 没有 IDR → 解码器无法初始化 → 永远黑屏

**修复**：
1. encoder.rs：添加 `force_keyframe()` 方法，调用 `openh264::Encoder::force_intra_frame()`
2. peer.rs：添加 `force_keyframe: Arc<AtomicBool>` 标志，首帧默认 `true`
3. peer.rs：`run_video_stream_loop` 每 3 秒（`KEYFRAME_INTERVAL_SECS`）自动强制 IDR
4. peer.rs：暴露 `request_keyframe()` 方法供外部调用

### 根因 2：write_sample 失败后不退出循环（peer.rs）

`write_sample` 返回 Err 时只 warn 不 break，即使客户端已断开，streaming loop 仍然无限发包。

**修复**：连续 3 次 write_sample 错误后 break 退出循环。

### 根因 3：MSE codec 字符串硬编码不匹配（view.rs）

JS 中 `addSourceBuffer('video/mp4; codecs="avc1.42E01F"')` 硬编码，但实际 SPS 是 `42C028`。avcC 里的 profile/constraint/level 与 MSE codec 字符串不匹配时，浏览器可能拒绝初始化 SourceBuffer。

**修复**：
1. ViewerCallback trait：`on_video_init` 增加 `codec_str: String` 参数
2. GuiCallback / viewer_loop.rs：传递 `(init_b64, codec_str)` 元组
3. view.rs：使用 muxer 的 `codec_string()` 动态生成 codec，添加 fallback 到 `avc1.42E01F`

## H.264 黑屏修复（第五轮）🔴 核心根因

用户报告：IDR 帧正常到达、SPS 解析 1920x1080、fMP4 init/segments 正常生成、codec 字符串 `avc1.42C028` 正确传递，但仍然黑屏。

### 根因：fMP4 stsd/dref box 的 `entry_count` 被多余 `w32(0)` 推成 0（muxer.rs）

**致命 Bug**：`stsd_box()` 和 `dref_box()` 在 data 前面多加了一个 `w32(0)`（注释写着 "version+flags"），但 `full_box()` 已经自动添加 version+flags。导致：

```
实际输出: [size][stsd][version=0][flags=0] [0x00000000] [0x00000001] [avc1/avcC...]
                                                  ↑ 多余!      ↑ 真正的 entry_count
浏览器解析: version=0, flags=0, entry_count=0 → 无 sample entry → 无 codec 描述 → 解码器无法初始化
```

**后果**：
- stsd entry_count=0 → avc1/avcC 编码描述完全不可见 → H.264 解码器不启动
- dref entry_count=0 → 无数据引用 → 轨道无效
- 两者叠加导致 MSE SourceBuffer 虽然创建成功（codec 字符串在 addSourceBuffer 时独立指定），但 init segment 解析失败，所有后续 media segment append 也失败

**修复**：移除 `stsd_box()` 和 `dref_box()` 中多余的 `w32(&mut data, 0)`
- 修复后 init segment 从 681 字节减少到 673 字节（减少 8 字节 = 2 × 4 字节多余 w32）

### DataChannel 事件队列满修复

**错误**: `Failed to send RTCDataChannelEvent to data channel 1: Full(OnBufferedAmountLow)`

**根因**: input DataChannel 只有 `dc.send()` 使用，没有 poll 循环消费内部事件。
webrtc-rs 驱动向所有 DataChannel 推送 `OnBufferedAmountLow` 等事件，
input DC 无人消费导致有界事件队列被填满。

**修复**: 在 `on_data_channel` 的 input 分支添加事件 draining 循环，
poll 消费 `OnClose`/`OnError`（退出循环）和其他事件（丢弃），
空闲时每 `CLIPBOARD_POLL_MS` 毫秒检查一次。

### RTP 包队列满修复（视频轨道事件通道溢出）

**错误**: `Failed to send RtpPacket to track ...: Full(OnRtpPacket(Packet { ... }))`

**根因**: `on_track` 中单个 spawned task 同时做 `track.poll()` 和
`process_rtp_payload()`（含 H264 解包 + OpenH264 解码 + JPEG 编码）。
JPEG 编码在 marker 包到来时触发，耗时较长，阻塞了后续 RTP 包的消费，
导致 webrtc-rs 内部有界通道被填满后丢包。

**修复**: 拆分为双任务流水线：
- **快通道**: 只管 `track.poll()` → `pkt_tx.send(payload, marker)`，不做任何处理
- **慢通道**: 从 `pkt_rx.recv()` 取包 → `process_rtp_payload()` → JPEG → callback
- 使用 `unbounded_channel` 确保快通道 send 永不阻塞

用户放弃 fMP4/MSE 路径，改用浏览器原生 `RTCPeerConnection + ontrack + video.srcObject`。编译通过但连不上。

### 根因 1：SDP 中 `\r` 未转义导致 JS SyntaxError 🔴 核心问题

webrtc-rs 生成的 SDP 使用 CRLF (`\r\n`) 行尾。客户端转发 SDP 到 JS 时，只转义了 `\n` → `\\n`，但 `\r` (0x0D) 作为原始字节留在 JS 单引号字符串中。JS 规范禁止字符串字面量中包含未转义的行终止符（包括 CR），导致 `document::eval()` 执行的 JS 产生 SyntaxError → `handleOffer()` 从未被调用 → 无 Answer SDP → 连接永远建立不起来。

**修复**：改用 `serde_json::to_string(&sdp)` 生成 JSON 编码的字符串（自动处理 `\r\n`、引号、Unicode 等所有特殊字符），直接嵌入 JS 代码。JSON 字符串也是合法的 JS 字符串字面量。同样修复了 ICE candidate 的转义问题。

### 根因 2：`<video>` 元素与 ontrack 竞态

`<video>` 元素仅在 `rtc_connected=true` 后才渲染到 DOM，但 `ontrack` 在 SDP 协商阶段（ICE 完成之前）就触发。此时 `document.getElementById('remote-video')` 返回 null → `srcObject` 未设置 → stream 丢失。

**修复**：
1. 始终渲染 `<video>` 元素，未连接时 `display:none`
2. JS `ontrack` 处理器将 stream 存储到 `window._rtcStream` 全局变量
3. 新增 `use_effect`：当 `rtc_connected` 变为 true 时，检查 `_rtcStream` 并 late-bind 到 video

### 根因 3：`on_connected()` 从未被调用

`ViewerCallback::on_connected()` 是空实现，没有任何代码路径调用它 → `SessionState::Connected` 永远不会被设置 → 连接成功后 UI 仍显示"连接中"。

**修复**：在 JS 轮询检测到 `pc.connectionState == "connected"` 时，直接设置 `vs.state.set(SessionState::Connected)`。

## Pure Rust 客户端回放旧画面 + 鼠标坐标修复

用户反馈：连接成功但客户端持续回放旧的远程桌面界面（不更新）；鼠标点击后 remote 没反应。

### 修复 1：depacketize 失败后清理 NAL buffer（decoder.rs）🔴

`process_rtp_payload()` 中当 `depacketize()` 返回 Err 时，之前直接 `return None` 但**不清理 `nal_buffer`**。腐败数据残留在 buffer 中，后续 marker 包到来时 `decode_frame()` 会用腐败数据 + 新数据一起解码 → OpenH264 可能触发 error concealment 返回上一帧缓存 → 画面卡在旧帧。

**修复**：`Err` 分支增加 `self.nal_buffer.clear()` 再返回 None。

### 修复 2：track.poll() None 分支添加 sleep（viewer.rs）

快通道 poll loop 中 `_ => {}` 匹配 `None`（无 RTP 包可用）时无限 CPU 空转。

**修复**：显式匹配 `None` 并 `sleep(1ms)`。

### 修复 3：PLI 首次请求延迟优化（viewer.rs）

原实现 `tokio::time::sleep(3s)` 在 PLI 发送**之前**执行 → 连接建立后等 3 秒才发第一个 PLI 请求 keyframe → 客户端可能错过首帧 IDR 后长时间无法解码。

**修复**：先立即发送一次 PLI，再进入 3 秒间隔循环。

### 修复 4：诊断日志增强

- decoder.rs：解码错误从 `debug!` 提升到 `log::warn!`
- viewer.rs：慢通道添加帧计数器 + 每 5 秒进度日志 + 首帧详情日志（尺寸、JPEG 字节数）
- viewer_loop.rs：UI 帧计数器，每 30 帧输出一次日志

### 修复 5：running=false 导致 track poll task 立即退出的时序 bug 🔴🔴🔴 致命根因

**用户反馈**：鼠标点击有反应（host 能收到），但画面永远是旧的。

**根因**：`on_track()` 在 `pc.set_remote_description(offer)` **内部**触发，但 `running.store(true)` 在这之后才执行。导致：

```
set_remote_description(offer)
  ├─ on_track() 触发 → spawn 三个 task
  │    ├─ fast poll task: while running.load() { } → false → 立即退出
  │    ├─ slow decode task: while pkt_rx.recv() → sender 已 drop → 立即退出
  │    └─ PLI task: 发了一次 PLI → while running.load() { } → false → 退出
  ├─ (返回)
create_answer() → set_local_description() → running.store(true)  ← 太晚
```

PLI 确实发出去了，host 也发了 keyframe，但 fast task 已经退出 → RTP 包从不被消费。

**修复**：将 `running.store(true, Ordering::SeqCst)` 移到 `set_remote_description` 之前。同时在各 Err 分支加 `running.store(false)` 回退。

### 修复 6：流式解码 + NAL 逐单元处理（decoder.rs）🔴

**用户反馈**：client 很多 Decode 失败，屏幕延迟 3-4 秒。

**根因 1：旧实现 NAL buffer 累积多帧**
- 旧代码 `nal_buffer` 累积所有 NAL，只有 marker 到达时才 decode
- 丢包时 `nal_buffer` 包含多个帧的 NAL → decode 时混在一起 → OpenH264 返回 error concealment（旧帧）或解码失败
- 延迟累积：慢通道处理速度跟不上快通道收包速度

**根因 2：`unbounded_channel` 无界导致队列无限增长**
- fast task 收包速度 >> slow task 处理速度（30fps vs decode+JPEG 50ms/帧）
- `pkt_rx` 队列无限增长 → 延迟累积到 3-4 秒

**修复**：
1. **流式解码**：删除 `nal_buffer`，每个 NAL 单元 depacketize 后立即送 `self.decoder.decode(&nal)`
2. **marker 时 flush**：`marker=true` 时调用 `self.decoder.flush_remaining()` 获取所有缓存帧
3. **就地 YUV→RGB**：不在函数间传递 `yuv`（避免生命周期冲突），在 `process_rtp_payload` 内就地完成 YUV→RGB→JPEG
4. **Slow task 跳帧**：`viewer.rs` slow task 改用 `loop { recv().await + try_recv() drain }`，总是处理最新帧，跳过中间帧
5. **编译错误修复过程**：
   - E0425: `DecodedYUV` 不在 `openh264::formats` → 改用 `impl YUVSource`
   - E0599: `YUVSource` trait 没有 `write_rgb8()` 方法 → 不在函数间传递 `yuv`，就地处理
   - E0499: `for nal` 循环内调用 `self.convert_and_store(yuv)` 与 `self.decoder.decode()` 同时借用 `self` → 删除 `convert_and_store()`，在循环内就地转换 YUV→RGB

### 修复 7：PLI 首次立即发送（viewer.rs）

**根因**：原实现 `sleep(3s)` 在 PLI 发送之前，连接建立后等 3 秒才发第一个 PLI。

**修复**：先立即发送一次 PLI，再进入 3 秒间隔循环。

### 修复 8：帧级跳帧替代包级丢弃（decoder.rs + viewer.rs）🔴🔴🔴

**用户反馈**：改了 drain-to-latest 后变成"丢包，一直解码失败"。

**致命根因**：H.264 一个帧被切分到几十个 FU-A RTP 包里，drain-to-latest 只保留最后一个包 → 解码器收到残缺 NAL 片段 → 持续解码失败。

**正确做法**：包级不能跳，帧级可以跳。

**修复**：
1. `decoder.rs`：`process_rtp_payload()` 改为返回 `Option<(Vec<u8>, u32, u32)>`（原始 RGB），不再内部做 JPEG。`rgb_to_jpeg()` 独立为公开方法。
2. `viewer.rs` slow task：处理**所有** RTP 包（不跳过任何包），每个包都送 decoder；只在 drain 周期结束时对**最后一帧**做一次 JPEG 编码。

**效果**：
- 全量解码（不丢包）→ 零解码失败
- JPEG 编码只做一次/周期 → 延迟可控
- 帧级跳帧（保留最新 RGB）→ 天然低延迟

### 修复 9：初始 burst 延迟 + 解码错误（skip-to-latest-frame + keyframe 请求）🔴🔴

**用户反馈**：client 未准备好时 host 已大量包过来（开始显示10秒前界面），并经常出错（Native:4 dsInvalidArgument, Native:18 dsRefLost）。

**根因 1：初始 burst**
- host 从连接起以 30fps 发包，client 的 slow task 需要处理所有旧包才能到达最新帧
- 10 秒的包 = ~300 个包 = ~10 帧，逐帧 decode + JPEG 需要处理全部

**根因 2：没有 keyframe 参考帧**
- 连接后最先收到的可能是 P-frame（没有 IDR），解码器返回 Native:18（dsRefLost）
- 138KB 的大 NAL（IDR）在没有 SPS/PPS 的情况下被送入解码器 → Native:4

**修复**：
1. **decoder.rs**:
   - 添加 `reset()` 方法 — 重置 depacketizer + decoder（清空参考帧和 FU-A 累积状态）
   - 添加 `has_decoded_frame` 标志 — 首帧前抑制大量 decode error 日志
   - `process_rtp_payload()` 返回 `(Option<RGB>, bool)` — bool 表示是否需要 keyframe
   - depacketize 失败时自动重置 depacketizer（防止腐败数据毒化后续帧）
